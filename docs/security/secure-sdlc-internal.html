Secure Software Development Lifecycle (SDLC) & Secure Review Policy

Effective date: January 1, 2026
Owner: Chief Technology Officer
Applies to: sayhii core backend services, desktop applications, mobile applications, web applications, and analytics systems

1. Purpose​

This policy defines the principles and high-level practices sayhii follows to design, develop, review, test, and release software securely. The objective is to reduce the likelihood and impact of security defects, protect customer data, and maintain trust, while remaining proportional to the size, risk profile, and maturity of the organization.

This policy is intentionally principles-based and technology-agnostic. Detailed procedures and tooling may evolve over time without requiring changes to this policy.

2. Scope​

This policy applies to the development and maintenance of sayhii software systems, including:

  • Core backend services
  • Desktop applications
  • Mobile applications
  • Web applications
  • Analytics and data processing pipelines

Compliance with this policy is required for all in-scope software development activities.

3. Guiding Principles​

sayhii follows these guiding principles when developing software:

  • Security is everyone’s responsibility. Secure design and implementation are shared responsibilities across all contributors.
  • Risk-based decision making. The depth of security review and testing is proportional to the risk of the change.
  • Preventative controls are preferred. Where feasible, preventative controls (e.g., design safeguards, automated checks) are favored over detective or reactive controls.
  • Least privilege and isolation. Systems are designed to minimize access, prevent cross-tenant exposure, and limit blast radius.
  • Continuous improvement. Secure development practices are reviewed and improved over time as the organization and product evolve.

4. Change Initiation and Classification​

Development work may begin through ad hoc branching or planned feature development. Changes are generally classified informally as one or more of the following:

  • New features or enhancements
  • Bug fixes
  • Maintenance or refactoring

Certain changes are considered higher risk and receive increased scrutiny. These may include, but are not limited to:

  • Authentication or authorization logic
  • Handling of personally identifiable information (PII)
  • Data access controls or anonymization logic
  • Cross-tenant data boundaries

Risk classification is determined by the developer and reviewer based on professional judgment and system impact.

5. Secure Design Considerations​

When designing or modifying software, developers consider security implications as part of normal design activities, including:

  • Data exposure and sensitivity
  • Authentication and authorization boundaries
  • Tenant isolation and cross-organization access controls
  • Encryption in transit and at rest
  • Application of anonymization and aggregation rules for reporting

Higher-risk changes may involve additional review, design discussion, or consultation prior to implementation.

6. Development and Code Review​

6.1 Development Practices​

  • Changes are developed in isolated branches.
  • Direct commits to protected branches are not permitted.
  • Secure coding practices are applied throughout development.

6.2 Code Review​

  • All externally contributed code is reviewed prior to merge.
  • Internal code changes are reviewed using a risk-based approach.
  • Reviews consider functional correctness, maintainability, and security implications.

In environments with limited staffing, review practices may be adapted while maintaining accountability and security awareness.

7. Automated and Preventative Controls​

Where feasible, development workflows incorporate automated controls, which may include:

  • Automated builds and validation
  • Unit or integration testing
  • Static analysis or linting
  • Dependency analysis

Automated controls are intended to prevent defects from reaching production and to support consistent enforcement of development standards.

8. Testing and Validation​

Changes are validated prior to production release through a combination of:

  • Local developer testing
  • Deployment to non-production environments
  • Manual functional verification

Higher-risk changes may receive additional validation focused on security-relevant behavior.

9. Release and Deployment​

  • Production releases are manually approved and executed by authorized personnel.
  • Deployment access is restricted according to access control policies.
  • Deployment activity is logged through version control and delivery systems.

Emergency changes may be deployed to address urgent issues. Such changes are reviewed after deployment to confirm correctness and identify improvements.

10. Production Access​

Direct access to production systems may be used for operational purposes under strict access controls. Access is limited, monitored, and granted only where necessary to support system reliability or incident response.

11. Post-Deployment Monitoring and Response​

After release, systems are monitored through logging, alerts, and customer feedback. Identified issues are investigated and addressed in accordance with incident response and remediation processes.

Rollback or mitigation actions may include reverting changes, redeploying prior versions, or disabling affected functionality.

12. Vulnerability Management​

Identified vulnerabilities, including third-party dependency issues, reported security concerns, or configuration weaknesses, are evaluated for impact and remediated in a timely manner when relevant.

13. Continuous Improvement​

Secure development practices are periodically reviewed and refined based on:

  • Operational experience
  • Security incidents or near-misses
  • Product evolution and organizational growth

Improvements may be documented in procedures, standards, or tooling without requiring changes to this policy.

Appendix A: Evidence Examples (Informative)​

Evidence supporting this policy may include, where applicable:

  • Version control history and branch records
  • Pull request reviews and approvals
  • Automated build and test logs
  • Deployment and release records
  • Architecture or design documentation

This appendix is illustrative and does not require all evidence types to exist for every change.
